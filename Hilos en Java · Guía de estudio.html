Vídeo 1

Creación de hilos

¿Qué es un hilo?

Un hilo es un flujo de ejecución: una "línea" de instrucciones que la CPU va recorriendo una detrás de otra. Todo proceso tiene al menos uno, el hilo principal (main), que ejecuta el contenido del método main. Dentro de un hilo las instrucciones son siempre secuenciales.

El problema: tareas independientes ejecutadas en fila

Imagina un programa que prepara el desayuno. Hacer tostadas no necesita nada del café, y viceversa. Sin hilos, el programa hace primero una tarea entera y después la otra:

public class Desayuno {
    static void prepararTostadas() throws InterruptedException {
        System.out.println("Ponemos el pan a tostar");
        Thread.sleep(2000);          // simula una espera de 2 s
        System.out.println("Echamos la sal");
        Thread.sleep(2000);
        System.out.println("Tostadas listas");
    }
    static void prepararCafe() throws InterruptedException {
        System.out.println("Ponemos la cafetera");
        Thread.sleep(2000);
        System.out.println("Servimos el café");
        Thread.sleep(2000);
        System.out.println("Café listo");
    }
    public static void main(String[] args) {
        try {
            prepararTostadas();      // 4 s
            prepararCafe();          // 4 s  -> total 8 s
        } catch (InterruptedException e) { e.printStackTrace(); }
    }
}
¿Por qué Thread.sleep()?Es un método estático (no hace falta crear un Thread para llamarlo) que detiene el hilo actual unos milisegundos. En clase lo usamos para simular trabajos lentos reales: una petición web, una consulta a base de datos, una descarga. Para la CPU, 300 ms es una eternidad.
InterruptedExceptionCuando sleep puede lanzar esta excepción, Java te obliga a elegir: rodearlo con try/catch o declarar throws InterruptedException en el método. Declararla permite un único try/catch en el main en lugar de uno por método. Pero ojo: dentro de run() no puedes poner throws, porque estarías cambiando la firma del método heredado; allí el try/catch es obligatorio.

Forma 1: heredar de Thread

class Tostadora extends Thread {
    @Override
    public void run() {              // lo que se ejecutará en el hilo
        try {
            System.out.println("Ponemos el pan a tostar");
            Thread.sleep(2000);
            System.out.println("Tostadas listas");
        } catch (InterruptedException e) {
            System.out.println("Hilo interrumpido");
        }
    }
}
// En el main:
Tostadora t = new Tostadora();
t.start();            // lanza el hilo
prepararCafe();       // el main sigue y ambas tareas se intercalan

Forma 2: implementar Runnable (la recomendada)

Runnable es una interfaz con un único método sin implementar: run(). Como Runnable no tiene start(), hay que envolverla en un Thread:

class Tostadora implements Runnable {
    @Override
    public void run() { /* mismo código de antes */ }
}
// En el main:
Thread t = new Thread(new Tostadora());   // el constructor recibe un Runnable
t.start();
prepararCafe();
¿Por qué es mejor Runnable?En Java una clase solo puede heredar de una clase. Si Tostadora extiende Thread, ya no puede extender nada más. Implementando una interfaz te queda libre la herencia.

Dos detalles que suelen fallar

  • El orden importa. Si llamas a prepararCafe() antes de t.start(), el café se hace entero (4 s) y solo entonces arranca el hilo: no hay concurrencia y tarda el doble.
  • El orden de salida cambia. El planificador del sistema operativo decide cómo se intercalan los hilos, así que cada ejecución puede mostrar las líneas en distinto orden.
Ejemplo mentalDescargar 10 archivos: sin hilos, el décimo espera a que terminen los nueve anteriores. Con un hilo por descarga, avanzan todos a la vez.

Creación de hilos con clases anónimas y expresiones lambda

Son dos sintaxis para escribir lo mismo con menos código, cuando la clase del hilo solo se va a usar una vez.

Clase anónima

Una clase sin nombre que implementa una interfaz (o clase abstracta) y se define e instancia justo donde se necesita:

public static void main(String[] args) {
    Thread t = new Thread(new Runnable() {
        @Override
        public void run() {
            System.out.println("Preparando café en otro hilo");
        }
    });
    t.start();
    prepararTostadas();
}
No se instancia la interfazAunque se lea new Runnable(), Java no crea una instancia de la interfaz (imposible en cualquier lenguaje): el compilador genera por debajo una clase sin nombre que la implementa y crea un objeto de esa clase.

Reglas de acceso (clase anónima y lambda)

La clase anónima está anidada en la clase que la contiene, y eso condiciona lo que puede tocar:

Elemento¿Leer?¿Modificar?
Atributos y métodos de la clase padre (p. ej. contador)SíSí
Variables locales del método donde se defineSíNo (deben ser final o effectively final)
public class Main {
    static int contador = 0;                // atributo
    public static void main(String[] args) {
        String texto = "Contando";          // variable local
        Thread t = new Thread(new Runnable() {
            public void run() {
                for (int i = 0; i < 5; i++) {
                    contador++;                     // OK: atributo
                    System.out.println(texto + " " + contador);  // OK: solo leer
                    // texto = "otra";             // ERROR de compilación
                }
            }
        });
        t.start();
    }
}

Expresión lambda (desde Java 8)

Una lambda es un bloque de código con parámetros de entrada y, opcionalmente, un valor de retorno: básicamente un método sin nombre que se pasa como argumento. Sintaxis: (parámetros) -> { código }.

Thread t = new Thread(() -> {      // () porque run() no recibe parámetros
    System.out.println("Hola desde una lambda");
});
t.start();
¿Cuándo se puede usar una lambda?Cuando un método o constructor espera un objeto de una interfaz con un único método abstracto (interfaz funcional). Runnable cumple: solo tiene run().
Regla prácticaSi ese trozo de código lo usas en un solo sitio: lambda o clase anónima. Si lo necesitas en varios lugares: crea una clase con nombre que implemente Runnable y reutilízala.

Información sobre hilos

Cada hilo guarda atributos que se consultan con getters de la clase Thread y, en algunos casos, se cambian con setters.

MétodoQué devuelve / hace
getId()Identificador numérico único, asignado al crear el hilo. No se puede cambiar. (En Java 19+ se recomienda threadId().)
getName() / setName(String)Nombre del hilo; por defecto Thread-0, Thread-1… (el principal se llama main). Útil para identificarlos en la salida.
getPriority() / setPriority(int)Prioridad de 1 a 10. Constantes: Thread.MIN_PRIORITY (1), NORM_PRIORITY (5, valor por defecto), MAX_PRIORITY (10). Más prioridad = más preferencia del planificador (no garantía absoluta).
getState()Estado actual (solo lectura), un valor de Thread.State.
isAlive()true si el hilo ya arrancó y aún no ha terminado.

Los estados de un hilo

EstadoSignificado
NEWCreado, pero aún no se ha llamado a start().
RUNNABLEEjecutándose (o listo para hacerlo) en la CPU.
BLOCKEDBloqueado esperando un recurso ocupado (un fichero, una zona de memoria).
WAITINGEspera indefinida hasta que ocurra un evento (wait(), join() sin tiempo).
TIMED_WAITINGEspera de duración limitada (sleep, o wait/join con timeout).
TERMINATEDHa ejecutado todas sus instrucciones.

Ejemplo: consultar los atributos de un hilo lanzado

Thread t = new Thread(() -> {
    for (int i = 0; i < 5; i++) {
        System.out.println("Hola, soy un hilo");
        try { Thread.sleep(1000); } catch (InterruptedException e) {}
    }
});
t.setName("Saludador");
t.setPriority(Thread.MAX_PRIORITY);
System.out.println(t.getState());   // NEW (aún sin start)
t.start();
System.out.println(t.getName() + " | prioridad " + t.getPriority()
                   + " | estado " + t.getState() + " | vivo " + t.isAlive());
// Probablemente: TIMED_WAITING, porque el hilo está dentro del sleep

Que un hilo consulte sus propios datos

Thread.currentThread() es un método estático que devuelve el objeto Thread del hilo que está ejecutando esa línea:

Thread yo = Thread.currentThread();
System.out.println(yo.getName());    // "main" si lo llamamos en el main
System.out.println(yo.getState());   // RUNNABLE: si está ejecutando esta línea, está corriendo

Esperar a que otro hilo termine (versión "a mano")

t.start();
while (t.isAlive()) {                // o: t.getState() != Thread.State.TERMINATED
    try { Thread.sleep(1000); } catch (InterruptedException e) {}
}
System.out.println("Adiós");         // se muestra al acabar el hilo
No es la mejor soluciónCon espera corta gastas CPU comprobando sin parar; con espera larga pierdes tiempo tras terminar el hilo. La solución buena es join() (vídeo 4).
Vídeo 4

Suspensión de hilos

Suspender un hilo es detener su ejecución de forma temporal: porque espera una condición, la liberación de un recurso, el fin de otro hilo, o simplemente para no saturar. Ejemplo típico: una app de chat que pregunta al servidor "¿hay mensajes nuevos?" cada 100-200 ms. Para el usuario parece instantáneo, pero no se hacen miles de peticiones inútiles por segundo.

Las cuatro herramientas

1. Thread.sleep(ms)

Suspende el hilo actual el tiempo indicado en milisegundos. Exige capturar InterruptedException.

2. TimeUnit

Hace lo mismo con más legibilidad, porque eliges la unidad y no calculas milisegundos:

import java.util.concurrent.TimeUnit;
TimeUnit.SECONDS.sleep(2);        // 2 segundos
TimeUnit.MILLISECONDS.sleep(500); // 500 ms
TimeUnit.MINUTES.sleep(2);        // 2 minutos (en vez de 120000)

Conviene conocerla porque muchos métodos de concurrencia reciben un objeto TimeUnit como parámetro.

3. Thread.yield()

No suspende nada por sí mismo. Es un aviso al planificador: "no estoy haciendo nada importante, si quieres ceder la CPU a otro hilo, adelante". Puede ser ignorado.

4. join()

Suspende el hilo que lo llama hasta que termine el hilo sobre el que se invoca. Es una llamada bloqueante.

Thread t = new Thread(() -> {
    Random r = new Random();
    for (int i = 0; i < 10; i++) {
        try { Thread.sleep(r.nextInt(1500)); } catch (InterruptedException e) {}
        System.out.println(i);
    }
});
t.start();
try {
    t.join();                         // el main se queda esperando aquí
} catch (InterruptedException e) { e.printStackTrace(); }
System.out.println("El hilo ha finalizado");   // siempre después del 9
Espera activa vs. join()Un while(t.isAlive()){} es una espera activa: preguntas "¿has terminado?" sin parar y ocupas CPU, impidiendo incluso que el otro hilo avance. Con join() el hilo duerme y el sistema lo despierta justo cuando el otro acaba: sin gasto y sin retrasos.

5. wait() (adelanto)

Suspende el hilo hasta recibir una notificación (notify) de que debe continuar. Se estudiará con la sincronización de hilos.

Vídeo 5

Finalización de hilos con flags

Muchos hilos ejecutan tareas repetitivas un número de veces desconocido: en una videollamada, un hilo envía vídeo y otro lo recibe, cada uno en un bucle hasta que se cuelga. Hay que poder decirles "para".

No uses stop()Existe Thread.stop(), pero está obsoleto (deprecated) por problemas de seguridad: corta el hilo en cualquier punto y puede dejar datos a medias. Las dos alternativas son los flags y las interrupciones.

El flag: una variable booleana

Sustituimos el while(true) (mala práctica) por while(ejecutar) y damos al hilo un método para ponerla a false:

class Cafetera implements Runnable {
    private volatile boolean ejecutar = true;   // el flag
    private int contador = 0;

    public void detener() { ejecutar = false; }
    public int getContador() { return contador; }

    @Override
    public void run() {
        while (ejecutar) {
            try {
                Thread.sleep(200); System.out.println("Ponemos la cafetera");
                Thread.sleep(200); System.out.println("Servimos el café");
                Thread.sleep(200); System.out.println("Echamos la leche");
                contador++;
                System.out.println("Cafés preparados: " + contador);
            } catch (InterruptedException e) { }
        }
    }
}

public class Main {
    public static void main(String[] args) throws InterruptedException {
        Cafetera c = new Cafetera();
        Thread t = new Thread(c);
        t.start();
        new Scanner(System.in).nextLine();   // espera a que pulses Enter
        c.detener();                         // ponemos el flag a false
        t.join();                            // ¡esperamos a que termine de verdad!
        System.out.println("Total: " + c.getContador() + " cafés");
    }
}
Detalle sobre volatileAl compartir una variable entre hilos conviene declararla volatile para garantizar que el hilo de la cafetera vea el cambio hecho desde el main. (En el vídeo no se usa; es un añadido de buena práctica.)

Qué ocurre al llamar a detener()

El hilo no se detiene al instante. Si está a mitad de un café, termina todas las instrucciones del cuerpo del bucle, incrementa el contador y solo al volver a comprobar while(ejecutar) sale. Ventaja: la tarea en curso siempre se completa.

Sin join() el resultado puede ser falsoSi el main muestra getContador() justo tras detener(), el hilo puede estar aún preparando el café nº 5: el main imprimiría 4 y el hilo después terminaría el 5. Regla: si un hilo principal quiere un resultado calculado por otro, debe hacer join() primero.

Este método sirve en cualquier lenguaje de programación y es muy utilizado por su sencillez.

Vídeo 6

Finalización de hilos con interrupciones

Es el mecanismo específico de Java. Se llama a t.interrupt() y se le envía al hilo una señal de interrupción. Qué ocurre depende de lo que esté haciendo el hilo:

Situación del hiloEfecto de interrupt()
Suspendido (sleep, wait, join)Ese método lanza InterruptedException. Con ello la interrupción queda "gestionada" y el indicador interno vuelve a false.
Ejecutando código normalNo salta ninguna excepción; solo se marca el indicador, y isInterrupted() devolverá true.

Error típico: el try/catch dentro del bucle

// MAL: el hilo NO termina
public void run() {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            Thread.sleep(200);
            // ... preparar café ...
        } catch (InterruptedException e) {
            System.out.println("Hilo interrumpido");
        }                 // tras el catch, isInterrupted() es false → sigue el bucle
    }
}

La excepción se captura, el indicador se pone a false al haberse gestionado, la condición del while dice "no interrumpido" y el hilo continúa haciendo cafés por mucho que pulses Enter.

Solución: el bucle dentro del try

// BIEN
public void run() {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            Thread.sleep(200); System.out.println("Ponemos la cafetera");
            Thread.sleep(200); System.out.println("Servimos el café");
            Thread.sleep(200); System.out.println("Echamos la leche");
            contador++;
        }
    } catch (InterruptedException e) {
        System.out.println("Hilo interrumpido");   // salimos del bucle y de run()
    }
}
// En el main:  t.interrupt();  t.join();

Ahora la excepción saca al hilo del bucle directamente y run() termina.

Consecuencias a tener en cuenta

  • El café puede quedar a medias. Si la excepción salta durante un sleep, no se ejecuta el resto del cuerpo (ni el incremento del contador). Con flags, la iteración siempre se completa; con interrupciones, no.
  • La condición del while sigue siendo necesaria. Si el hilo está ejecutando código largo sin sleep/join/wait, ninguna excepción saltará y solo isInterrupted() nos avisará. Hay que consultarlo nosotros.
// Hilo que hace cálculos sin métodos que suspendan
while (!Thread.currentThread().isInterrupted()) {
    // ... muchas instrucciones ...
    contador++;                       // esta iteración SÍ se completa
}
// Al volver a la condición, detecta la interrupción y sale
Elegir entre flags e interrupcionesFlags: simples, universales, la iteración termina limpia. Interrupciones: despiertan al hilo aunque esté dormido o esperando, pero requieren más cuidado con la excepción y la posición del try/catch.
Vídeo 7

Memoria compartida

Hasta ahora los hilos eran independientes. Pero a veces varios hilos hacen partes de una misma tarea o uno necesita el resultado de otro. Una técnica para comunicarlos es la memoria compartida: que varios hilos accedan al mismo espacio de memoria, es decir, al mismo objeto.

Sin compartir vs. compartiendo

class Contador implements Runnable {
    private int contador = 0;
    public void run() {
        for (int i = 0; i < 100; i++) contador++;
        System.out.println(Thread.currentThread().getName() + ": " + contador);
    }
}

// SIN compartir: una instancia por hilo (5 contadores) → cada hilo acaba en 100
for (int i = 1; i <= 5; i++) {
    Contador c = new Contador();
    new Thread(c, "Hilo " + i).start();
}

// COMPARTIENDO: una sola instancia para los 5 hilos → un único contador
Contador c = new Contador();
for (int i = 1; i <= 5; i++) new Thread(c, "Hilo " + i).start();   // el total llega a 500

La única diferencia es dónde se hace el new Contador(): dentro del bucle (uno por hilo) o fuera (uno para todos). Con lambdas es igual: una variable local dentro de la lambda es de cada hilo; si la sacas fuera como atributo static (el main es estático y solo accede a atributos estáticos), todos comparten una.

Resultados extrañosCon 100 iteraciones los hilos muestran valores desordenados (300, 400, 100…) porque se alternan, aunque el contador acabe en 500. Con 1 millón de iteraciones por hilo el total debería ser 5 millones, pero no llega y cambia en cada ejecución: son problemas de concurrencia.
Lo peligrosoPuedes ejecutar el programa 200 veces sin fallo y que falle la siguiente. En producción puede pasar una vez al mes. Con un punto de ruptura (breakpoint) además el fallo desaparece, por eso es tan difícil de depurar.

Condición de carrera y sección crítica

Condición de carreraComportamiento del software cuyo resultado depende del orden en que se ejecutan las operaciones concurrentes. Si al cambiar el orden de los hilos obtienes un resultado distinto, hay condición de carrera. Aparece al acceder o modificar un recurso compartido.
Sección críticaEl conjunto de instrucciones que acceden o modifican un recurso compartido.

Ejemplo de la cuenta bancaria (se reutiliza en los siguientes vídeos)

Dos hilos comparten una Cuenta: uno hace 1000 ingresos de 100 € y otro 1000 reintegros de 100 €. El saldo final debería ser 0.

class Cuenta {
    private int saldo = 0;
    public int getSaldo() { return saldo; }
    public void ingresar(int cantidad)  { saldo += cantidad; }   // sección crítica
    public void reintegrar(int cantidad){ saldo -= cantidad; }   // sección crítica
}
class HiloIngreso implements Runnable {
    private Cuenta cuenta;
    public HiloIngreso(Cuenta c) { this.cuenta = c; }
    public void run() { for (int i = 0; i < 1000; i++) cuenta.ingresar(100); }
}
// HiloReintegro es idéntico, pero llama a cuenta.reintegrar(100)

public static void main(String[] args) throws InterruptedException {
    Cuenta c = new Cuenta();                       // el MISMO objeto para ambos
    Thread t1 = new Thread(new HiloIngreso(c));
    Thread t2 = new Thread(new HiloReintegro(c));
    t1.start(); t2.start();
    t1.join();  t2.join();
    System.out.println("Saldo final: " + c.getSaldo());   // -900, -300... ¡no siempre 0!
}
¿Dónde está la sección crítica?En ingresar() y reintegrar(), porque ambos modifican saldo. No en el run() de cada hilo: ahí solo se llama a esos métodos. Además, con pocas operaciones (p. ej. 10) el error casi no aparece, pero el código sigue siendo incorrecto.
Vídeo 9

Monitores

La exclusión mutua garantiza que si un hilo está ejecutando una sección crítica, ningún otro puede ejecutarla. Java la implementa con monitores, que gestiona internamente: tú no los creas ni los instancias, pero conviene entender cómo funcionan.

MetáforaEl monitor es un guardia de seguridad con una única llave. Un hilo con la llave entra a la sección crítica y no la devuelve hasta terminar; los demás esperan fuera.

Todo objeto es un monitor

El mecanismo está en la clase Object, de la que heredan todas las clases, así que cualquier objeto puede actuar como monitor. Hay dos usos válidos: que un objeto controle sus propias secciones críticas (el objeto cuenta protege ingresar y reintegrar), o que una instancia cualquiera (por ejemplo, de una clase Perro) controle las secciones críticas de otro objeto.

Las tres zonas de un monitor

ZonaQué es
Entry setLa cola de entrada: hilos que piden ejecutar una sección crítica.
OwnerEl hilo que posee el monitor (tiene la "llave") y ejecuta la sección crítica.
Wait setHilos suspendidos esperando una notificación (se ve en el vídeo 11).

Ejemplo paso a paso

  • HiloReintegro quiere ejecutar reintegrar() y pasa al entry set. Como nadie es owner, el monitor le da la llave: adquiere el monitor.
  • HiloIngreso quiere ejecutar ingresar(). El monitor ve que hay un owner y lo deja esperando en el entry set.
  • Cuando HiloReintegro termina, libera el monitor y HiloIngreso pasa a ser el owner.
Vídeo 10

Métodos y bloques sincronizados

El código es sencillísimo; lo difícil es detectar las secciones críticas y entender qué ocurre por debajo.

Métodos sincronizados

Basta con añadir la palabra reservada synchronized. Si un hilo ejecuta uno de ellos, ningún otro hilo puede ejecutar ninguno de los métodos sincronizados de ese objeto (el propio objeto es el monitor):

class Cuenta {
    private int saldo = 0;
    public synchronized void ingresar(int cantidad)   { saldo += cantidad; }
    public synchronized void reintegrar(int cantidad) { saldo -= cantidad; }
    public int getSaldo() { return saldo; }
}
// Ahora el saldo final es siempre 0

Limitación: necesitas poder modificar la clase. Si viene de una librería ya compilada, no puedes añadirle synchronized.

Bloques sincronizados

Se pone synchronized y entre paréntesis el objeto que hará de monitor, alrededor de la sección crítica. Así no tocas la clase Cuenta:

// En HiloIngreso.run()
for (int i = 0; i < 1000; i++) {
    synchronized (cuenta) {            // monitor = cuenta
        cuenta.ingresar(100);
    }
}
// En HiloReintegro.run()
for (int i = 0; i < 1000; i++) {
    synchronized (cuenta) {            // ¡el MISMO monitor!
        cuenta.reintegrar(100);
    }
}
El monitor debe ser el mismoPuede ser cualquier objeto (en clase se usó una instancia de Perro compartida por ambos hilos), pero los bloques que quieras excluir entre sí deben usar el mismo objeto. Si un hilo usa perro y el otro cuenta, hay dos monitores: dos hilos no ejecutarán ingresar a la vez, pero sí un ingreso y un reintegro a la vez, y el error vuelve.
DiseñoSi tienes 4 fragmentos que no pueden ejecutarse a la vez entre sí, necesitas un monitor compartido por esos 4. Si otros 2 fragmentos son independientes de los anteriores pero exclusivos entre ellos, necesitan otro monitor distinto.

Métodos wait y notify

Resuelven cómo hacer que un hilo avise a otro de que ocurrió un evento. Caso: el hilo de reintegros no debe sacar dinero si el saldo es menor de 100. Un bucle con sleep funciona pero es ineficiente (espera de más o consume CPU). La solución son wait() y notify(), métodos de Object disponibles en todos los objetos.

  • wait(): suspende el hilo (pasa al wait set) y libera el monitor.
  • notify(): despierta a uno de los hilos que esperan en ese mismo objeto. notifyAll() los despierta a todos.
// HiloReintegro.run()
for (int i = 0; i < 1000; i++) {
    synchronized (cuenta) {
        while (cuenta.getSaldo() < 100) {          // ¡while, no if!
            System.out.println("No hay saldo suficiente");
            try { cuenta.wait(); }                  // espera y libera el monitor
            catch (InterruptedException e) { return; }
        }
        cuenta.reintegrar(100);
    }
}

// HiloIngreso.run()
for (int i = 0; i < 1000; i++) {
    synchronized (cuenta) {
        cuenta.ingresar(100);
        cuenta.notify();                            // avisa: hay saldo
    }
}

Qué ocurre, en orden

  • El hilo de reintegros posee el monitor, ve saldo 0 y llama a wait(): pasa al wait set y suelta el monitor.
  • El de ingresos entra, ingresa y llama a notify(). El de reintegros se despierta, pero pasa al entry set a esperar turno.
  • Cuando el de ingresos sale del bloque y libera el monitor, el de reintegros lo adquiere, vuelve a comprobar la condición y, si hay saldo, reintegra.
Reglas obligatorias
  • wait y notify solo dentro de un bloque o método synchronized; si no, el compilador da error.
  • wait siempre dentro de un while con la condición, nunca un if, para evitar los spurious wake-ups: te despiertan, pero otro hilo ya dejó la cuenta a 0, así que hay que recomprobar.
  • notify no cede la ejecución: el que notifica sigue hasta liberar el monitor; el planificador decide cuándo corre el otro.

Interbloqueos (deadlock)

Con varios recursos compartidos aparece el interbloqueo: dos hilos se quedan esperando indefinidamente un monitor que tiene el otro, y la aplicación se cuelga. Ocurre en una transferencia entre cuentas A y B, o al reservar varios asientos: hay que bloquear varios recursos.

static Object A = new Object(), B = new Object();

static void hilo1() {
    synchronized (A) {                       // bloquea A...
        dormir(100);
        synchronized (B) { System.out.println("Hilo 1 tiene A y B"); }   // ...y quiere B
    }
}
static void hilo2() {
    synchronized (B) {                       // bloquea B...
        dormir(100);
        synchronized (A) { System.out.println("Hilo 2 tiene B y A"); }   // ...y quiere A
    }
}
public static void main(String[] args) {
    new Thread(Main::hilo1).start();         // referencia a método
    new Thread(Main::hilo2).start();
}

El hilo 1 tiene A y espera B; el hilo 2 tiene B y espera A. Ninguno cede: interbloqueo (el sleep solo sirve para forzarlo en el ejemplo).

Referencia a métodoMain::hilo1 equivale a la lambda () -> hilo1(). Solo vale si el método no recibe parámetros, porque no se ponen paréntesis (llamarías al método en lugar de pasarlo).

Regla de oro: bloquear siempre en el mismo orden

Si hilo2 también bloquea primero A y luego B, el primero que llegue lo ejecuta entero y libera ambos; el segundo espera y no hay deadlock.

Cuando el orden no lo controlas: el inventario de jugadores

Un método intercambiar(origen, destino) bloquea ambos inventarios. Un hilo llama intercambiar(aitor, beatriz) y otro intercambiar(beatriz, aitor): orden cruzado, deadlock. Pedir al programador "usa siempre el mismo orden" es una solución chapucera: tu código debe protegerse solo. La solución correcta: dar un identificador único a cada recurso y bloquear siempre de menor a mayor ID, ordenando dentro del método:

class Inventario {
    private final int id = new Random().nextInt();   // identificador (en real, único de verdad)
    public int getId() { return id; }
    // ... nombre, objetos, quitar(), añadir() ...
}

static void intercambiar(Inventario origen, Inventario destino) {
    if (origen.getId() > destino.getId()) {          // ordenamos por ID
        Inventario aux = origen;                      // variable auxiliar para el intercambio
        origen = destino;
        destino = aux;
    }
    synchronized (origen) {
        synchronized (destino) {
            // quitar el objeto al origen real y dárselo al destino real
        }
    }
}
Ojo con la lógica realAl reordenar, la variable origen ya no es necesariamente de quien sale el objeto. En el vídeo se simplifica con un contador; en un caso real conserva aparte quién es el emisor y quién el receptor, y usa el orden por ID solo para bloquear. Un Random puede repetir IDs; en un sistema real el identificador debería ser realmente único (p. ej. desde una base de datos).
